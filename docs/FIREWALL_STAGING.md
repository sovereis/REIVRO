# Rework Firewall staging candidate

This integration adds a staging path for public pull requests. The local Firewall CLI, the VERIFY sandbox and Early Access remain separate entry points.

## Trust boundaries

- The staging database stores immutable GitHub repository and App installation IDs, a trusted base branch, memberships, analysis/runs, findings, protections and attributed events. Compound foreign keys prevent cross-project links. A client's repository ID is a lookup key. Authorization depends on the authenticated Supabase JWT subject and its provisioned membership for that repository.
- PostgREST must expose only the dedicated `reivro_checks_api` schema for this feature. Its function is an invoker wrapper. The privileged dispatcher is in the unexposed `reivro_cloud` schema with a fixed empty search path and explicit grants. Humans can read their own project's records under RLS using an authenticated PostgreSQL context. PostgREST exposes an invoker `read_run` RPC for evidence lookup by repository and Check external ID. It applies the same RLS and returns null for an inaccessible run. Reviewers use guarded commands, viewers cannot mutate, and the dedicated worker Auth user receives only claim/finish authority for the mapped installation and repository. Provision membership and project rows out of band. No new key belongs in the frontend, and the PostgreSQL `service_role` receives no grants here.
- A project-row lock serializes review, approval, revocation and run finalization. The subscription worker must supply the same authenticated subject that claimed the run. Unique delivery and revision keys suppress replay even if the unsigned delivery ID changes. The reviewed manifest digest binds approval to exact UTF-8 bytes. Revocation is terminal and rechecked inside the finish transaction.
- The worker validates HMAC-SHA256 on the original body before parsing, checks the App installation, repository ID, PR number, expected base branch and SHAs, and corroborates the revision using authenticated GitHub REST. It reads the manifest only from the pinned base commit at a fixed path, checking its Git blob hash and approved SHA-256. It never loads rules or runs scripts from the PR checkout. VERIFY v2 compiles source in its existing seccomp subprocess with an empty environment, memory, time and output limits.
- The check is published for the exact claimed HEAD with the database run ID as `external_id`. The Check contains fixed summaries instead of untrusted source or diagnostic text. Full evidence lives in the run and findings. `VIOLATION` maps to failure, `PASS` to success, a `review_required` decision (including `ERROR` and `INCONCLUSIVE`) to action required, and `INACTIVE` and `OBSERVED` to neutral. With no approved protection, the analysis can collect a finding for review and reports `OBSERVED` when it completes conclusively.

## Reproduce locally

```sh
scripts/test-firewall-staging.sh
```

The harness starts disposable PostgreSQL 17 with networking disabled, applies the SQL and runs standard PostgreSQL roles, RLS, transactions and concurrency tests. It uses a stub Supabase Auth schema and injects fixture UUIDs after the place where a real gateway would validate the JWT. The test uses a real isolated VERIFY compiler and disposable Git index, and substitutes GitHub REST/Checks responses. No live Auth session, staging project or GitHub Check is created by the harness.

The lifecycle test signs a PR delivery, finds a syntax regression without an active guard, rejects unauthenticated and unauthorized review attempts, confirms with the reviewer identity and approves the exact proposal digest. It stages the bytes in Git and reads them from the index as the trusted-base fixture. The second PR produces a failure Check for its pinned HEAD. A clean PR produces success. Modified artifact bytes yield neutral. Revocation during an execution wins if committed before finalization. The test also covers a replay with a different delivery ID, concurrent approval and claim attempts, and a second project that cannot read or mutate the first project's data.

## Pilot setup for review

1. Verify an isolated Supabase ref, PostgreSQL major version, separate roles and keys, and the absence of production data or shared credentials. Review the migration and enable the dedicated API schema only in that staging project. Validate Supabase Auth and actual Data API grants with two project reviewers and a separate worker account. Provision mappings through a privileged administrative session. A human JWT must come from the staging Auth service.
2. Install a GitHub App only in a repository you control, after reviewing its configuration. Grant repository **Metadata read**, **Pull requests read**, **Contents read**, and **Checks write**. Subscribe to pull request deliveries and narrow the installation token to the pilot repository. Leave required checks and branch protection unchanged. Use a trusted worker checkout with Linux/CPython and libseccomp.
3. Pass authenticated raw webhook deliveries to `python -m server.scop_firewall_checks --publish-staging-check` on stdin. Set `REIVRO_WEBHOOK_EVENT`, `REIVRO_WEBHOOK_DELIVERY` and `REIVRO_WEBHOOK_SIGNATURE` from the headers. The trusted process sets `REIVRO_REPOSITORY`, `REIVRO_REPOSITORY_ID`, `REIVRO_INSTALLATION_ID`, `REIVRO_TRUSTED_BASE` and `REIVRO_STAGING_REF`. Supply `REIVRO_WEBHOOK_SECRET`, `REIVRO_GITHUB_INSTALLATION_TOKEN`, `REIVRO_WORKER_JWT` and `REIVRO_PUBLISHABLE_KEY` through server configuration. This adapter consumes a token issued and refreshed by the operator or hosting layer. It does not own an App private key or mint or refresh tokens.
4. A reviewer calls `read_run` with the Check external ID and repository ID using their Supabase Auth JWT, then uses the finding ID from that response to call the staging review RPC. Request parameters are a registered `repository_id`, a finding or protection UUID in `subject`, and a `reason`. Call `confirm` or `reject`, then `propose` for a confirmed finding. Review the returned manifest text and digest. Call `approve` with the protection UUID and digest, then place the returned manifest bytes unchanged at `.reivro/protections/python-syntax-regression.json` on the trusted base using your normal reviewed Git process. Call `revoke` with the same protection UUID and digest to disable it; changing Git alone cannot authorize a guard.
5. Test live with two controlled PRs and a follow-up clean PR. Compare Check timestamps, reported HEADs, audit run IDs and revocation outcomes. Verify that a JWT from another project and a revoked worker membership fail closed before any wider use.

This is a single-delivery worker with no hosted ingress or queue. A network failure after the Checks POST may leave publication uncertain. Search for the external run ID before retrying manually. An interrupted claim remains recorded and is deduplicated. There is no automated recovery or backfill. A revocation after database finalization does not retract a historical Check; a later run uses current state. PostgreSQL administrators and the trusted worker are security boundaries. The worker can attest verifier evidence, but cannot approve it. The pilot only supports public PRs and one active syntax protection per project.

## Cost estimate

For a pilot of 1,000 deliveries/month at an assumed 30 seconds of worker occupancy per delivery, plan about 8.3 worker-hours/month before retries and hosting minimums. At a hypothetical $0.05–$0.15 per worker-hour this is roughly $0.42–$1.25 in variable compute. Storage, egress, hosting minimums, any queue, and Supabase plan charges are separate. Supabase advertises a Pro plan starting at $25/month; Free eligibility and availability must be checked before provisioning. These are planning assumptions, not measured costs or a billing quote. ## Hosted pilot checklist and approval gates

- [ ] **Owner approves the staging target and any spend.** Record the organization, isolated project ref, PostgreSQL major version, region, plan, and credentials owner. Compare the database host, API URL and Auth issuer with the staging dashboard. Confirm that staging uses distinct signing keys, tokens and data. Stop if it shares production data or configuration.
- [ ] **Database owner approves schema changes.** First run the local harness. In a verified staging-only PostgreSQL service configuration with TLS certificate verification, check the resolved project host and then run `psql 'service=reivro_pilot_staging' -X -v ON_ERROR_STOP=1 -f supabase/staging/001_firewall.sql`. Expose `reivro_checks_api` only after reviewing the gateway configuration. Keep `reivro_cloud` outside the exposed schemas. Confirm schema/table/function grants and RLS with staging identities before storing evidence.
- [ ] **Provision and verify Auth identities.** Assign a reviewer in project A, a different reviewer in project B, a read-only viewer and a dedicated App worker. Register the actual GitHub repository and installation IDs in `projects` and populate `memberships` through an admin session. Obtain short-lived staging JWTs from Supabase Auth and exercise `read_run` and `dispatch` over the hosted Data API. Confirm project B receives no project A evidence, a viewer cannot approve and the worker cannot act as a reviewer. Record the authorization results without storing tokens.
- [ ] **Repository owner approves App installation and webhook delivery.** Install only on the controlled public demo repository. Verify the App's granted permissions and the installation ID in GitHub, then mint a short-lived installation token scoped to that repository and the approved permissions. Configure HTTPS ingress, request bounds, raw-body preservation, the webhook secret in the secret store, and the worker environment from the pilot setup above. Leave required status checks unchanged.
- [ ] **Run the pilot on controlled PRs.** Send one signed delivery and confirm the observed regression and review audit trail. Approve the exact proposal digest and version its bytes on the trusted base. Deliver a later regression and a clean change. Compare Check conclusions, HEADs, external IDs, artifact digests and run records. Verify invalid signature, duplicate delivery, and revocation. Record timestamps, GitHub request counts, elapsed worker time, hosted charges and limitations.
- [ ] **Reconcile publication before any manual retry.** If the worker reports `PUBLICATION_UNCERTAIN`, list check runs on the claimed HEAD and match the App, check name and external run ID. A missing or inconsistent response is not confirmation. Escalate to the pilot operator before reprocessing; automatic redelivery cannot issue a second POST for the same claimed revision.

The worker validates the returned HEAD, external ID, completed status and conclusion before reporting confirmed publication. An unavailable or invalid artifact cannot authorize a favorable decision. Independent verified regressions are retained. A transient artifact provider failure remains operationally retryable when there is no verified regression to preserve. A Check records the state at database finalization. Later revocation changes future evaluation, and the previously published Check remains historical evidence.
