# Productivity measurement v0.7

This local experiment interface records workflow outcomes and explicit human feedback separately. It follows the acceptance and timing requirements in the official MVP PRD. The existing [Workspace v0.6](WORKSPACE.md) interface is unchanged.

## Setup and commands

Use Python 3.12 on Linux with an owner-only local directory outside Git worktrees. Choose a dedicated store for each experiment.

```sh
store=$(mktemp -d /tmp/scop-experiment.XXXXXX)
python -B -m server.scop_measurement --store-dir "$store" <<'JSON'
{"operation":"run","permissions":["local:write-measurements"],"request":{"pr_url":"https://github.com/pallets/flask/pull/5808","permissions":["github:read-pr-evidence"]}}
JSON
```

Copy the execution UUID from `result.workspace.execution.execution_id`. After reviewing the result, send a request with your actual decision and observed timings. The following request body is **illustrative test data**. Replace the UUID and values with your own. Omit unknown values.

```json
{
  "operation": "feedback",
  "permissions": ["local:write-measurements"],
  "execution_id": "00000000-0000-4000-8000-000000000000",
  "evaluation": {
    "decision": "accepted",
    "review": {"milliseconds": 1200, "provenance": "human_measured"},
    "rework": {"milliseconds": 0, "provenance": "human_reported"},
    "correction_cycles": 0
  }
}
```

Pass each request on stdin to the same command. The other operations are:

| Request body | Result |
| --- | --- |
| `{"operation":"get","execution_id":"<uuid>"}` | Technical record, human evaluation if supplied, and derived timings. |
| `{"operation":"aggregate"}` | Counts and rates for the local dataset. |
| `{"operation":"aggregate","complete_observation_set":true}` | Adds completion rate when the study operator attests that every attempted workflow in the cohort is captured. |
| `{"operation":"export"}` | Aggregate metrics and de-identified observation rows on stdout. Redirect to a private destination only when you intend to retain a copy. |

The response has `contract_version: "0.7"`, `result`, and `error`. The run result embeds Workspace v0.6 output. Status exit codes follow Workspace for runs, while invalid measurement operations exit 1 and denied local-write grants exit 2. There is no endpoint for importing caller-supplied execution outcomes. Use the measurement interface to run the task when you want to evaluate it later.

## Feedback and missing data

A completed technical record is eligible for feedback. The CLI records one immutable decision per execution, either `accepted` or `needs_rework`. A second submission is rejected. Unknown IDs and technically failed, blocked, or cancelled executions cannot receive feedback. A run leaves evaluation null until an explicit decision is supplied. The original technical status stays unchanged.

Feedback timestamps are generated by the server in UTC and validated when read. Client timestamps are rejected. Review and rework each accept an integer duration from zero through seven days in milliseconds and one provenance value, `human_measured` for timing taken by the reviewer or `human_reported` for a retrospective estimate. An explicit zero means the activity was observed or reported as absent. Omitted or null fields mean unknown. Correction cycles may be supplied as an integer from 0 through 10,000. Optional notes are capped at 1,000 characters. Keep credentials, names, private diffs, and other sensitive data out of notes.

## Metric definitions

| Metric | Formula and unit | Provenance and missing data |
| --- | --- | --- |
| Execution duration | Elapsed workflow time in milliseconds | System-observed by Workflow v0.5. |
| Human review and human rework | Supplied milliseconds for each activity | Human-measured or human-reported, as labeled. Each unknown duration is null. |
| Total observed task time | Sum of known execution, review, and rework milliseconds | Derived from the available components. Complete only when both human durations are known. Record zero explicitly for a component known to be inapplicable. Partial totals can be lower than actual time. |
| Acceptance rate | Accepted evaluations ÷ eligible evaluations with a decision | Derived from explicit human decisions on completed runs. Unreviewed runs are excluded. |
| Rework rate | Needs-rework evaluations ÷ eligible evaluations with a decision | Derived from the same decision set. A correction-cycle count is a separate observation. |
| Citation coverage | Matched references ÷ references checked | Derived from workflow counts, pooled across references for aggregate results. Includes partial comparisons from failed verification. Measures matching, with semantic judgment left to reviewers. |
| Workflow completion rate | Technically completed executions ÷ attempted executions | Derived from the recorded cohort after explicit completeness attestation. Without it the numerator, denominator, and value are null. |

Ratios are unitless fractions reported with numerator and denominator. A zero denominator yields null. Transport rejections and attempts lost to process or storage failures do not have a durable execution row. Reconcile study attempts separately before asserting completeness. Local records hold only the fields needed for these metrics. Export drops execution IDs, timestamps, URLs, and notes. Unusual timings or correction counts can still make an observation recognizable in a small cohort.

## Storage and permissions

The local write grant applies only to run recording and feedback. GitHub permission is separate and remains read-only. Fetches use the existing Workspace bounds. The dedicated directory must be mode 0700 and owned by the running user. Files are mode 0600. The store rejects symlinked path components and Git worktrees, uses descriptor-relative file operations and exclusive publication, and caps the cohort at 1,000 runs with at most one evaluation each. Request and record caps are 64 KiB and 8 KiB respectively, with a 2 MB CLI response cap. The CLI waits for stdin, so use caller-side timeouts where needed.

The same local OS user can directly alter or delete its own files. This store is not a tamper-proof audit log. An interrupted write may leave a pending entry. The index fails closed on unexpected entries. Investigate incompleteness before using the dataset. No hosted service, frontend, or automatic telemetry is included.

## Comparison protocol

1. Define a review task and acceptance rubric in advance. Use matched public PRs of similar size, language, and complexity. Use the same evidence requirements and review rubric in both arms.
2. Counterbalance assignment and order across reviewers. For an initial feasibility pilot, plan 10 matched task pairs and report the actual number, experience, PR characteristics, and missing observations. This pilot is exploratory and cannot establish a general productivity gain.
3. Start timing at task handoff with the same preparatory materials. End at first rubric-based acceptance or a fixed study cutoff. Track start/end wall time separately. Record active review and correction time without double-counting waiting or overlapping work. Use measured timings where possible and report self-reported records separately.
4. Log every attempt, including failed or blocked runs and manual fallback. Record each human correction cycle and the evaluator's final decision at the cutoff. A `needs_rework` decision is an outstanding result at cutoff. If a later review is needed, preserve the original evaluation and trace later work in the study log. This CLI stores a single evaluation, so multi-review histories belong in that log.
5. Compare paired elapsed time to acceptance, completion, acceptance, and correction burden. Report unsuccessful attempts and missing observations alongside timing summaries. Compare output quality under the same rubric before interpreting timing differences. Citation coverage alone provides no quality or productivity conclusion.

No experimental outcomes are included in this implementation.
